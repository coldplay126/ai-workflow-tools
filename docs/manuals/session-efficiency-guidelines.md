# Session Efficiency Guidelines

> 오케스트레이터-워커 A2A 환경에서 세션 유지, 세션 분리, 재브리핑, 위임의 효율을 판단하기 위한 운영 기준.
> 목표는 **토큰 효율 최적화**와 **문맥 오염/누락 최소화**를 동시에 달성하는 것이다.

---

## 1. 목적

이 문서는 다음 상황에서 사용할 수 있는 범용 기준을 정의한다:

- 오케스트레이터가 워커에게 작업을 위임할지 직접 수행할지 판단할 때
- 기존 세션을 유지할지 새 세션을 열지 판단할 때
- 새 세션 또는 워커에게 얼마만큼의 문맥을 전달해야 할지 결정할 때
- 긴 작업에서 토큰 비용과 정확도 저하를 동시에 관리할 때

이 문서의 핵심 질문은 다음 4가지다:

1. 이 작업은 **기존 세션에 남아 있어야 하는가**
2. 이 작업은 **새 세션으로 분리해야 하는가**
3. 이 작업은 **오케스트레이터가 직접 처리해야 하는가**
4. 이 작업은 **워커에게 최소 문맥으로 위임할 수 있는가**

---

## 2. 핵심 원칙

### G1. 필요한 문맥만 유지한다

문맥이 많을수록 항상 좋은 것이 아니다. 현재 작업의 품질에 실제로 기여하는 문맥만 유지한다.

### G2. 같은 목표의 연속 작업은 가능한 한 같은 세션에 둔다

같은 deliverable 묶음 안의 작업은 재브리핑 비용이 크므로, 특별한 이유가 없으면 같은 세션에서 이어간다.

### G3. 목표가 바뀌면 새 세션을 우선 검토한다

작업 대상, 도메인, 성공 기준이 바뀌면 이전 문맥은 자산보다 오염원이 될 가능성이 커진다.

### G3-1. 목표가 같아도 작업 모드가 바뀌면 분리를 검토한다

같은 목표를 유지하더라도 작업 모드가 `설계 -> 구현 -> 검증`으로 전환되면 필요한 문맥의 종류가 달라진다. 이 경우 세션을 반드시 분리해야 하는 것은 아니지만, **새 세션 또는 워커 분리**를 우선 검토한다.

### G4. 워커에는 전체 히스토리 대신 계약을 전달한다

워커는 긴 대화 이력보다 구조화된 목표, 입력, 제약, 참조 문서 목록을 받는 편이 효율적이다.

### G5. 세션 효율은 토큰 절감만으로 판단하지 않는다

토큰이 적게 들더라도 오해, 재작업, 누락이 늘어나면 전체 비용은 오히려 증가한다.

---

## 3. 용어 정의

### 세션

하나의 대화 스레드 또는 동일한 연속 문맥을 공유하는 작업 단위.

### deliverable 묶음

같은 목표를 향해 연결된 산출물 집합. 예:

- `constitution -> technical-specs -> phase plans`
- `spec -> implementation -> verification -> PR`

### 재브리핑 비용

새 세션 또는 워커에게 현재 상태를 정확히 전달하기 위해 필요한 요약 비용. 텍스트 길이뿐 아니라 중요한 규칙, 예외, 합의 사항의 수를 포함한다.

### 문맥 오염

이전 작업의 가정, 용어, 예외, 해결책이 현재 작업에 불필요하게 끌려와 판단을 흐리는 현상.

### 직접 의존 아티팩트

현재 작업이 직접 참조해야 하는 기존 문서, 코드, 상태 파일, 계약 파일.

- **강한 의존**: 없으면 작업이 성립하지 않는 계약/상태/핵심 설계 문서
- **약한 의존**: 참고하면 좋지만 없어도 작업을 진행할 수 있는 문서

### 세션 효율성

다음 4가지를 함께 고려한 효율:

- 토큰 사용량
- 재브리핑 비용
- 문맥 오염 위험
- 재작업/오판 가능성

---

## 4. 세션 유지 기준

아래 조건이 많을수록 기존 세션을 유지하는 편이 유리하다.

- 같은 목표를 향한 연속 작업이다
- 강한 의존 아티팩트가 1개 이상 있다
- 이전 산출물 2개 이상을 직접 참조한다
- 과거 합의, 예외, 용어 정의가 정확히 이어져야 한다
- 새 세션으로 옮기면 10줄 이상 재브리핑이 필요하다
- 배경 설명보다 실제 작업 비중이 크다
- 문맥 누락 시 품질 저하 위험이 크다

대표 예시:

- 설계 문서군 연속 리뷰
- 하나의 기능에 대한 spec 검토 후 구현 전 준비
- 같은 PR 범위 안에서 plan, verify, review를 연속 수행

---

## 5. 새 세션 시작 기준

아래 조건이 많을수록 새 세션이 유리하다.

- 목표가 바뀌었다
- 레포, 시스템, 도메인이 바뀌었다
- 목표는 같지만 작업 모드가 `설계 -> 구현`, `구현 -> 검증`으로 바뀌었다
- 이전 산출물에 대한 직접 의존이 거의 없다
- 새 세션에서 10줄 내외로 충분히 재브리핑할 수 있다
- 이전 문맥이 현재 판단에 편향을 줄 가능성이 크다
- 과거 합의를 자주 다시 확인하고 있다

대표 예시:

- 설계 검토에서 실제 코드 구현 단계로 전환
- 다른 레포의 버그 조사로 이동
- 이전 작업과 독립적인 문서 작성

---

## 6. 오케스트레이터 vs 워커 판단 기준

### 오케스트레이터가 직접 처리해야 하는 경우

- 전역 목표와 산출물 구조를 정해야 한다
- 여러 워커 결과를 통합해야 한다
- 계약, 우선순위, 승인 조건을 정해야 한다
- 즉시 다음 결정을 막는 critical path 작업이다
- 하위 작업이 충분히 분리되지 않았다

### 워커에게 위임하기 좋은 경우

- 작업 경계가 명확하다
- 입력과 기대 산출물이 분명하다
- 직접 의존 파일/문서가 제한적이다
- 다른 작업과 병렬 수행이 가능하다
- 결과를 구조화된 형태로 회수할 수 있다

### 워커에게 넘기면 안 되는 경우

- 오케스트레이터가 바로 다음 단계 결정을 위해 즉시 결과가 필요하다
- 범위가 애매하거나 중간에 방향이 바뀔 가능성이 크다
- 여러 하위 시스템을 가로지르는 전역 판단이 필요하다

---

## 7. 정량 휴리스틱

아래 수치는 절대 기준이 아니라 운영용 휴리스틱이다.

| 지표 | 유지 쪽 신호 | 분리 쪽 신호 |
|------|-------------|-------------|
| 강한 의존 아티팩트 수 | 1개 이상 | 0개 |
| 직접 의존 아티팩트 수 | 2개 이상 | 0-1개, 모두 약한 의존 |
| 꼭 기억해야 할 규칙/예외 수 | 10개 이하 | 20개 이상이면 과밀 경고 |
| 참조해야 하는 과거 턴 거리 | 최근 15턴 이내 | 30턴 이상 전 내용을 반복 참조 |
| 새 세션 재브리핑 길이 | 10줄 초과 | 10줄 이하 |
| 과거 합의 재확인 빈도 | 드묾 | 최근 3회 이상 반복 |
| 문맥 오염 위험 | 낮음 | 높음 |
| 작업 모드 전환 | 없음 | 설계/구현/검증 간 전환 있음 |

보조 해석:

- 핵심 참조 문서가 5개 이하이면 유지가 쉬운 편
- 핵심 참조 문서가 8개 이상이면 세션 분리 또는 문맥 축약을 검토
- 재브리핑이 25줄 이상 필요하면 유지가 대체로 유리

---

## 8. 토큰 효율 관점

세션 효율은 아래 두 비용의 균형이다.

### 유지 비용

- 긴 문맥을 매 턴 계속 끌고 가는 비용
- 과거 정보가 현재 답변에 불필요하게 섞이는 비용
- 오래된 합의가 현재 작업을 오염시키는 비용

### 재시작 비용

- 새 세션마다 배경을 다시 설명하는 비용
- 중요한 예외와 합의를 누락할 위험
- 워커가 배경 부족으로 재작업하는 비용

### 일반 규칙

- 같은 deliverable 묶음이면 유지가 대체로 더 싸다
- 다른 deliverable로 넘어가면 새 세션이 대체로 더 싸다
- 배경 설명보다 작업량이 크면 유지가 유리하다
- 작업보다 배경 복원이 커지면 분리가 유리하다

---

## 9. 세션 효율성 평가표

각 질문에 점수를 부여해 빠르게 판단한다.

### 유지 점수

- 같은 목표다: +2
- 강한 의존 아티팩트가 있다: +2
- 이전 산출물 2개 이상 직접 참조: +2
- 재브리핑 10줄 초과: +1
- 과거 합의 정확성이 중요: +2
- 새 세션에서 누락 위험이 큼: +2

### 분리 점수

- 목표가 바뀌었다: +2
- 다른 레포/도메인이다: +2
- 작업 모드가 바뀌었다: +2
- 재브리핑 10줄 이하 가능: +1
- 문맥 오염 위험이 크다: +2
- 과거 합의를 자주 재확인한다: +1

### 세션 판정

- `유지 점수 > 분리 점수` → 기존 세션 유지 권장
- `분리 점수 > 유지 점수` → 새 세션 권장
- 비슷하면 → 오케스트레이터는 유지, 워커는 새 세션 + 요약 전달

### 실행 판정

세션 판정 후, 실행 주체를 아래 4가지로 고정한다.

| 결과 | 의미 | 권장 상황 |
|------|------|----------|
| **유지-직접수행** | 기존 세션에서 오케스트레이터가 직접 처리 | critical path, 전역 판단 필요 |
| **유지-워커위임** | 기존 세션 유지 + 워커는 최소 문맥으로 별도 수행 | 같은 목표 안의 병렬 하위 작업 |
| **새세션-직접수행** | 새 세션으로 옮겨 오케스트레이터가 직접 처리 | 작업 모드 전환, 문맥 오염 위험 큼 |
| **새세션-워커위임** | 새 세션 또는 새 워커 스레드에서 독립 수행 | 다른 도메인, 재브리핑 짧음, 독립 작업 |

기본값:

- 세션은 유지지만 하위 작업이 분리 가능하면 `유지-워커위임`
- 작업 모드가 바뀌고 재브리핑이 짧으면 `새세션-직접수행`
- 다른 도메인/레포의 독립 작업이면 `새세션-워커위임`

## 10. A2A 실무 패턴

### 패턴 A: 설계 문서군 연속 검토

- 권장: 세션 유지
- 이유: 용어, 예외, 기준 문서가 서로 강하게 연결됨

### 패턴 B: 설계 -> 구현 전환

- 권장: 새 세션 검토
- 이유: 설계 문맥보다 코드/테스트 현실이 중요해짐

### 패턴 C: 구현 병렬화

- 권장: 워커 분리
- 이유: 모듈별 write scope가 분리되면 병렬 효율이 큼

### 패턴 D: 검증/리뷰 단계

- 권장: 오케스트레이터 유지 + 리뷰 워커 분리
- 이유: 전역 계약은 유지하되, 세부 검증은 병렬 위임 가능

### 패턴 E: 다른 도메인으로 전환

- 권장: 새 세션
- 이유: 이전 해결 패턴이 오히려 편향을 만들 수 있음

---

## 11. 워커 전달 규칙

워커에게는 가능한 한 아래 4가지만 먼저 전달한다.

1. 목표
2. 현재 상태
3. 핵심 제약
4. 참조 아티팩트

권장 형식:

```markdown
## Task
- 목표: ...
- 현재 상태: ...
- 제약: ...
- 참조: [fileA], [fileB]
- 기대 산출물: ...
```

워커에게 전체 세션 히스토리를 그대로 전달하는 것은 마지막 수단이다.

### 워커 응답 최소 계약

워커는 자유형 서술 대신 최소한 아래 항목을 포함해 응답한다.

```markdown
결론: 무엇을 완료했는가
근거: 어떤 문서/코드/상태를 근거로 판단했는가
변경 파일: 수정/생성한 파일 목록
남은 리스크: 아직 남아 있는 위험 또는 미확정 사항
오케스트레이터 결정 필요: 상위 판단이 필요한 항목
```

이 형식이 없으면 오케스트레이터의 통합 비용이 다시 증가한다.

---

## 12. 재브리핑 템플릿

새 세션 또는 워커 위임 시 다음 템플릿을 사용한다.

```markdown
목표: 무엇을 끝내야 하는가
현재 상태: 지금까지 무엇이 완료되었는가
핵심 제약: 반드시 지켜야 할 규칙/예외
참조 문서: 직접 읽어야 하는 파일 목록
```

추가가 필요할 때만 아래를 덧붙인다.

```markdown
열린 질문: 아직 결정되지 않은 것
기대 출력: 결과물 형식
검증 기준: 완료 판정 방식
```

---

## 13. 실패 신호

아래 신호가 보이면 세션 분리 또는 문맥 축약을 검토한다.

- 같은 배경 설명을 반복하고 있다
- 과거 합의가 무엇이었는지 자주 다시 확인한다
- 리뷰보다 문맥 복원에 더 많은 토큰을 쓰고 있다
- 워커 출력이 문맥 누락으로 자주 재작업된다
- 현재 작업과 무관한 과거 예외가 자꾸 판단에 끼어든다

---

## 14. 권장 운영안

- 세션 하나는 가능하면 하나의 deliverable 묶음까지만 유지한다
- 큰 작업은 `설계`, `구현`, `검증`으로 나눠 세션 분리를 검토한다
- 오케스트레이터는 전역 상태를 유지하고, 워커는 최소 문맥으로 일하게 한다
- 새 세션을 열 때는 반드시 재브리핑 템플릿으로 시작한다
- 토큰 절감보다 재작업 감소를 우선한다

### 운영 메트릭

운영 후 아래 지표를 추적하면 실제 효율 개선 여부를 확인할 수 있다.

- **재브리핑 평균 길이**: 새 세션/워커 시작 시 평균 요약 길이
- **워커 재작업률**: 1차 결과가 문맥 부족으로 재요청된 비율
- **동일 목표 내 세션 수**: 하나의 deliverable 묶음을 완료하는 데 사용된 세션 수
- **세션 전환 후 첫 산출물 수정률**: 새 세션 첫 결과가 크게 수정된 비율
- **통합 비용**: 오케스트레이터가 워커 결과를 정리하는 데 드는 추가 턴 수
- **문맥 오염 사례 수**: 이전 합의가 현재 작업을 잘못 이끈 사례 수

## 15. 빠른 체크리스트

세션 유지 전:

- 같은 목표인가?
- 이전 산출물 2개 이상을 직접 참조하는가?
- 새 세션에서 10줄 이내로 다시 설명 가능한가?
- 이전 문맥이 도움보다 오염 위험이 큰가?

워커 위임 전:

- 입력과 출력이 명확한가?
- write scope가 분리되어 있는가?
- 오케스트레이터가 즉시 결과를 필요로 하지 않는가?
- 전체 히스토리 없이도 작업 가능한가?
