# Multi-Agent Orchestration — 개념 개요

---

## 0. 에이전트 협업 패턴

멀티에이전트 시스템은 작업 특성에 따라 세 가지 협업 패턴 중 하나를 선택한다.

### 패턴 정의

| 패턴 | 관계 | 통신 | 적합한 작업 |
|------|------|------|-----------|
| **서브에이전트** | 부모→자식 (위임) | 결과만 부모에게 반환 | 결과만 필요한 집중 작업 |
| **에이전트 팀** | 동료 (협업) | 에이전트 간 직접 메시지 | 토론/반박이 가치 있는 작업 |
| **A2A** | 독립 서비스 (계약) | 표준 프로토콜 (HTTP) | 외부 시스템의 에이전트 연동 |

### 선택 원칙

- **기본은 서브에이전트**를 사용한다. 대부분의 파이프라인 작업은 결과만 필요하다.
- **에이전트 팀**은 에이전트 간 토론/반박이 품질을 높이는 경우에만 사용한다.
- **A2A**는 서로 다른 시스템의 에이전트를 연동할 때 사용한다.
- **설계 판단이 필요한 협업**에서는 human arbiter가 유효하다.

파이프라인별 적용표, 에이전트 팀 유효 조건, 도입 후보는 reference 문서를 참조한다.

## 1. 5가지 실행 모드

작업의 위험도와 복잡도에 따라 다섯 가지 모드 중 하나를 선택한다.

### solo — 단독 실행

Primary 에이전트 하나만 사용한다. 모든 작업의 기본 모드.

### quick — 읽기 전용

Secondary 에이전트 하나가 read-only로 빠르게 분석한다. Primary를 사용하지 않아 비용이 가장 낮다.

### precise — 순차 검증

Secondary가 먼저 분석하고, Primary가 그 결과를 검증하고 보완한다.

### cross — 병렬 교차 검증

두 Secondary 에이전트가 서로 다른 프로토콜로 독립 분석하고, Judge가 결과를 종합한다.

### critical — 순차 심층 체인

세 에이전트가 순차적으로 실행되며, 이전 결과가 다음 입력에 누적된다. 가장 높은 신뢰도.

### 모드 비교

| 모드 | 에이전트 수 | 실행 방식 | Judge |
|------|-----------|----------|-------|
| solo | 1 | 단독 | 불필요 |
| quick | 1 | 읽기 전용 | 불필요 |
| precise | 2 | 순차 | 선택적 |
| cross | 2 + Judge | 병렬 | 필수 |
| critical | 3 + Judge | 순차 체인 | 필수 |

모드별 상세 시퀀스, 프로토콜 매핑, 비용 비교는 reference 문서를 참조한다.

## 2. Policy-Based 승격/강등

### 자동 승격 (Auto-Promotion)

프롬프트의 키워드를 분석하여 위험도에 맞는 모드로 자동 승격한다.
보안 관련 키워드 → cross, 프로덕션 관련 키워드 → critical.

### 자동 강등 (Auto-De-escalation)

저위험 키워드가 감지되면 모드를 낮춘다. 불필요한 비용을 방지한다.

### 실행 중 강등 (Runtime De-escalation)

에이전트 실행 실패 시 하위 모드로 자동 강등한다.

승격/강등 키워드 목록과 구체 경로는 reference 문서를 참조한다.

## 3. Provider 추상화

오케스트레이터는 구체적인 AI 제공자를 직접 참조하지 않는다.
Provider Protocol과 Registry 패턴으로 추상화한다.

### 불변식

- 모든 Provider는 동일한 Protocol(인터페이스)을 구현한다
- Orchestrator는 Registry를 통해 이름으로 Provider를 조회한다
- Provider 교체 시 Orchestrator 코드 변경이 불필요하다

Provider Protocol 상세, 구현 유형(Subprocess/SDK/Mock), Registry 메서드는 status 문서를 참조한다.

## 4. 역할 기반 프로토콜 (Role-Based Protocols)

각 Secondary 에이전트는 역할(role)에 따라 다른 프로토콜을 할당받는다.
프로토콜은 외부 파일로 관리되며, 코드 수정 없이 동작을 변경할 수 있다.

### 프로토콜 원칙

- 역할 정의: 에이전트의 역할과 관점 명시
- 검증 기준: 무엇을 검증해야 하는지 항목화
- 응답 형식: 구조화된 JSON 스키마 명시
- 캐싱: 반복 로드를 방지하기 위해 TTL 기반 캐싱 적용

프로토콜 종류, 모드 매핑, 캐시 설정은 reference 문서를 참조한다.
