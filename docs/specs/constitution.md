# Constitution

> ai-workflow-tools의 모든 설계와 구현 판단의 기준.
> 이 문서의 원칙에 위배되는 구현은 허용하지 않는다.

---

## C1. 관찰과 판단을 분리한다

코드에서 **보이는 사실**(observation)과 그 사실에 대한 **판단**(judgment)은 서로 다른 단계에서, 서로 다른 역할이 수행한다.

- **관찰**: 엔드포인트 존재, 테이블 참조, import 의존성, 코드 패턴 — 심각도 없이 사실만 기록
- **판단**: 심각도 판정, 결론 도출, 권장 사항 — 관찰 결과를 입력으로 받아 수행

**왜**: 관찰과 판단이 뒤섞이면 확증 편향이 발생한다. "이슈가 있다"고 먼저 판단하면 증거를 선택적으로 수집한다. 사실을 먼저 모으고 나중에 판단해야 누락이 줄어든다.

**위반 신호**: Layer 2 observation에 `[High]`, `[Critical]` 등 심각도가 포함됨. Writer 프롬프트가 "이슈를 찾아라"로 시작함.

---

## C2. 계약으로 범위를 고정한다

실행 전에 **범위(scope)를 구조화된 계약으로 명시**하고, 실행 중/후에 계약 준수를 강제한다. 자유 형식 텍스트는 계약이 아니다.

- **plan-contract.json**: allowed_files, forbidden_paths, requirements, test_requirements
- **Writer/Judge 스키마**: claim, evidence, source_files, confidence
- **참조 확장 규칙**: 우선순위, 상한, 참조 이유

**왜**: 범위가 텍스트로만 존재하면 사후 검출만 가능하고, 위반이 누적된 후에야 발견된다. 구조화된 계약은 기계적 검증(diff ⊂ allowed_files)을 가능하게 한다.

**위반 신호**: impl이 plan에 없는 파일을 수정했는데 verify까지 모르고 있음. Writer 출력에 evidence 없이 claim만 존재함.

---

## C3. 기계가 잡을 수 있는 것은 기계가 잡는다

결정론적으로 검증 가능한 것(lint, typecheck, test, scope diff)은 **도구 실행으로 확인**하고, AI 리뷰에 위임하지 않는다.

- **결정론적 gate**: format → lint → typecheck → test. gate가 정의된 경우, 모두 통과해야 AI 리뷰 진입
- **scope gate**: changed_files ⊂ allowed_files, 위반 즉시 차단
- **baseline 필터**: 기존 오류는 기록하고, 신규 오류만 실패로 판정
- **gate 미정의 시**: gate를 skip하되, verify 결과에 "결정론적 검증 미실행" 경고를 기록하고 change class를 한 단계 보수적으로 승격한다. gate 부재 자체가 위반은 아니나, **신뢰도 저하를 명시적으로 기록**해야 한다

**왜**: AI에게 lint 오류를 분석하게 하는 것은 비용 낭비이자 불확실성 추가다. 도구가 확정적으로 판별하는 영역은 도구에게 맡기고, AI는 도구가 못 잡는 것(설계 적절성, 비즈니스 로직 정확성, 보안 패턴)에 집중한다.

**위반 신호**: gate가 정의되어 있는데 verify phase가 이를 실행하지 않음. gate 결과를 무시하고 AI 판단으로 override함. gate 미설정인데 경고 기록 없이 진행함.

---

## C4. 한 곳만 보면 틀린다

모든 분석과 수정은 **관련된 모든 코드 경로를 확인**한 후에 결론을 내린다. 서버만, 한 파일만, 한 관점만 보고 결론 내리지 않는다.

- **Writer 병렬 (기본)**: 문서화/리뷰 모드에서는 최소 2개 이상의 관점(구조/행위, 보안/품질/성능)으로 동시에 분석
- **조사 모드 예외**: investigation은 단일 Writer를 허용한다. 단, 이 예외는 **Code Path Inventory 필수 + 검증 수준 기록(C9)** 을 전제로 한다. 단일 관점이되 모든 관련 경로를 추적하고, 결론의 검증 수준을 명시해야 한다
- **Code Path Inventory**: 같은 기능을 건드리는 모든 경로를 사전에 식별
- **참조 확장**: 현재 unit의 observation → related domains → project context 순으로 맥락 확보

**왜**: CX 38건 분석에서 3건이 "한 곳만 보고 PR → 폐기" 패턴이었다. 서버 코드만 보고 수정했으나 실제 원인은 클라이언트(하드코딩 타이머), 다른 코드 경로(softDelete 누락), 클라이언트 SDK(AdMob 로드 실패)에 있었다.

**위반 신호**: investigation이 한 파일만 읽고 결론을 내림. 문서화/리뷰 모드에서 Writer가 1개뿐임. investigation이 Code Path Inventory 없이 단일 Writer로 실행됨. plan에 Code Path Inventory가 없음.

---

## C5. 위험도에 비례하여 투자한다

모든 작업에 동일한 파이프라인을 적용하지 않는다. **change class에 따라 review depth, 승인 경로, 격리 수준, gate 범위를 차등** 적용한다.

| 등급 | review depth | 승인 | 격리 | gate 범위 |
|------|-------------|------|------|----------|
| small | gate만 | auto 가능 | local | 변경 파일만 |
| standard | gate + AI 리뷰 | auto 조건부 | worktree | 변경 먼저 → 전체 |
| high-risk | gate + AI 리뷰 다수 + 사람 | 사람 필수 | isolated worktree | 전체 |

**왜**: 문서 오타 수정에 7-phase 전체를 돌리면 낭비이고, auth 리팩토링을 auto approve하면 위험하다. 리소스(시간, 토큰, 사람의 주의)는 유한하며, 위험도에 비례하여 배분해야 한다.

**위반 신호**: small 작업이 7단계를 전부 거침. high-risk 작업이 auto approve됨. 모든 작업에 동일한 gate_policy 적용.

---

## C6. 상태는 파일에 둔다

모든 실행 상태와 단계 간 전달 데이터는 **파일 시스템에 외부화**한다. LLM 대화 이력에 상태를 보관하지 않는다.

- **WF**: `.workflow/state.json`, `.workflow/artifacts/` (spec.md, plan.md, tasks.md, plan-contract.json)
- **Analysis**: `.analysis-state.json`, `.ai-context/`, `.tmp/stage1-xml/`
- **Knowledge**: `.work_history/`, `project-context.md`, `hashes.json`

**왜**: (1) LLM 세션은 휘발성이다. 컨텍스트 압축, 세션 종료, provider 교체로 상태가 사라진다. (2) 파일 기반이면 어떤 LLM이든 같은 상태를 읽을 수 있다(LLM 중립). (3) git으로 버전 관리, diff로 변경 추적이 가능하다.

**위반 신호**: phase 전환 시 이전 phase 결과를 대화 이력에서 참조함. 세션을 끊으면 작업을 이어갈 수 없음. 특정 LLM에서만 상태를 읽을 수 있음. 특정 LLM에서만 파이프라인을 실행할 수 있음(프롬프트, 호출 인터페이스, 출력 파싱이 특정 모델에 종속).

---

## C7. 역할을 분리하고 권한을 제한한다

하나의 역할이 계획, 실행, 검증을 모두 하지 않는다. 각 역할은 **명시된 권한만** 가진다.

| 역할 | 할 수 있는 것 | 할 수 없는 것 |
|------|-------------|-------------|
| Orchestrator | 상태 관리, 라우팅, phase 전환 | 코드 수정, AI 호출 |
| Executor | allowed_files 내 코드 수정 | forbidden_paths 접근, plan 변경 |
| Reviewer/Writer | 관점별 분석, claim 생성 | 코드 수정, 최종 판정 |
| Judge | claim 선별/병합, 일관성 검증 | evidence chain 수정, 새로운 claim 생성 |
| Gate | 도구 실행, pass/fail 판정 | AI 판단, 예외 허용 |

**왜**: 같은 모델이 계획하고 실행하고 검증하면 자기 검증 편향이 발생한다. 실행자가 자기 코드를 리뷰하면 문제를 못 본다. 역할 분리는 이 편향을 구조적으로 차단한다.

**위반 신호**: impl phase가 자기 코드를 verify함. Judge가 Writer의 evidence를 수정함. Executor가 plan-contract를 변경함.

---

## C8. 피드백은 구조화하고, 재시도는 예산 내에서 한다

실패 시 "FAIL + 사유 텍스트"가 아닌 **severity, location, suggestion이 명시된 구조화된 피드백**을 생성하고, 재시도 횟수에 예산을 둔다.

```
fix_feedback:
  severity: major | minor
  location: file:line
  category: scope_violation | lint | type_error | logic_error
  description: 무엇이 잘못되었는가
  suggestion: 어떻게 수정하는가
```

- **재시도 예산**: total_attempts(5), same_category_repeat_limit(2)
- **반복 이슈**: 같은 카테고리가 2회 반복되면 자동 수정을 포기하고 사람에게 에스컬레이션

**왜**: 비구조적 피드백은 재시도 시 같은 실수를 반복하게 한다. "scope violation"이라고만 알려주면 어디서 어떻게 위반했는지 모른다. 구조화하면 자동 수정이 정확해지고, 예산 없는 재시도는 비용을 폭발시킨다.

**위반 신호**: 피드백이 자유 텍스트로만 전달됨. 재시도 횟수에 상한이 없음. 같은 오류가 3회 이상 반복됨.

---

## C9. 재현 전에 확정하지 않는다

코드 분석 결과만으로 수정을 확정하지 않는다. 가능한 범위 내에서 **재현(또는 동등한 검증)을 거친 후** 확정한다.

- **검증 수준 기록**: 코드 분석만 / 유닛 테스트 / 통합 테스트 / 스테이징 재현 / 프로덕션 데이터 확인
- **investigation 모드**: 이슈 원인이 불명확할 때, 수정에 앞서 조사를 먼저 수행
- **에이전트 결과도 검증 대상**: LLM이 "원인은 X"라고 결론 내려도 재현 없이 신뢰하지 않는다

**왜**: CX 38건 중 PR 폐기 3건 모두 "코드 분석만으로 원인을 확정하고 수정에 들어간" 패턴이었다. 에이전트 분석도 확증 편향에 취약하며, 재현이 유일한 교정 장치다.

**위반 신호**: investigation 없이 바로 impl. verification_level이 기록되지 않음. 에이전트 결론을 검증 없이 plan에 반영.

---

## C10. 산출물은 목적에 따라 교체한다

**Layer 1-2는 공통**이고, 목적(mode)에 따라 **Layer 3 구성(Writer/Judge topology, 프롬프트, 권한)과 Layer 4 산출물을 교체**한다.

| 목적 | Layer 3 구성 | Layer 4 산출물 |
|------|-------------|---------------|
| 문서화 | Writer 2개(구조+행위) → Judge | .ai-context 4파일 |
| 리뷰 | Writer 3개(보안+품질+성능) → Judge | review-report.md |
| 조사 | 단일 Writer(opus, 코드 접근 권한) | investigation-report.md |

목적에 따라 달라질 수 있는 것: Writer 수, Writer별 역할/프롬프트, Judge 유무, 모델 선택, 코드 접근 권한.
목적이 달라져도 변하지 않는 것: Layer 1의 입력 수집, Layer 2의 observation 수집과 domain-bundle 생성.

**왜**: 목적마다 별도 파이프라인을 만들면 코드가 폭증하고, Layer 1-2의 개선이 모든 목적에 전파되지 않는다. 공통 기반 + 교체 가능한 끝단이 유지보수와 확장 모두에 유리하다.

**위반 신호**: 리뷰 모드용 Layer 2를 별도로 구현함. 새 목적 추가 시 Layer 1부터 복사함. Layer 2 개선이 문서화 모드에만 적용됨.

---

## C11. 세션은 작업 단위에 맞게 분리하고, 워커에는 최소 충분 문맥만 전달한다

오케스트레이터-워커 구조에서는 **세션 경계**를 작업 단위에 맞게 관리한다. 같은 목표와 강한 의존성을 가진 연속 작업은 같은 세션에 두되, 목표/도메인/작업 모드가 바뀌면 새 세션 또는 워커 분리를 우선 검토한다.

- **오케스트레이터 책임**: 전역 목표, 상태, 계약, 세션 연속성 판단 유지
- **워커 입력**: 전체 히스토리 대신 목표, 현재 상태, 핵심 제약, 참조 아티팩트 우선 전달
- **판단 기준**: 토큰 절감만이 아니라 재브리핑 비용, 문맥 오염, 재작업 가능성을 함께 고려
- **작업 모드 전환**: 같은 목표라도 `설계 -> 구현 -> 검증`으로 모드가 바뀌면 세션 분리를 검토

**왜**: 긴 세션을 무조건 유지하면 과거 합의와 예외가 현재 작업을 오염시킬 수 있고, 반대로 연결된 작업을 과도하게 분리하면 재브리핑 비용과 누락 위험이 커진다. 오케스트레이터는 전역 문맥을 유지하고, 워커는 최소 충분 문맥으로 국소 작업에 집중해야 전체 비용이 줄어든다.

**위반 신호**: 작업 모드가 바뀌었는데도 이전 세션을 그대로 끌고 가며 과거 합의를 반복 참조함. 워커에게 전체 히스토리를 그대로 넘겨 불필요한 문맥이 섞임. 새 세션을 열었는데 핵심 계약과 제약을 재브리핑하지 않음.

---

## 적용 우선순위

원칙 간 충돌 시 다음 순서로 우선한다:

1. **C9 재현 전에 확정하지 않는다** — 검증 없는 결과물은 어떤 원칙을 잘 따랐어도 무의미
2. **C1 관찰과 판단을 분리한다** — 나머지 모든 원칙의 전제
3. **C2 계약으로 범위를 고정한다** — 범위 없는 실행은 제어 불가
4. **C3 기계가 잡을 수 있는 것은 기계가 잡는다** — 비용 효율의 기본
5. **C7 역할을 분리하고 권한을 제한한다** — 편향 방지
6. **C4 한 곳만 보면 틀린다** — 품질
7. **C8 피드백은 구조화하고 재시도는 예산 내에서 한다** — 효율
8. **C5 위험도에 비례하여 투자한다** — 효율
9. **C6 상태는 파일에 둔다** — 인프라
10. **C11 세션은 작업 단위에 맞게 분리하고, 워커에는 최소 충분 문맥만 전달한다** — 운영 효율
11. **C10 산출물은 목적에 따라 교체한다** — 확장성

---

## 이 문서의 사용법

- **설계 판단 시**: "이 설계가 어떤 C 원칙을 위반하는가?" 검토
- **구현 리뷰 시**: "위반 신호"에 해당하는 패턴이 코드에 있는가 확인
- **기능 추가 시**: 새 기능이 10개 원칙 중 어떤 것과 긴장 관계에 있는지 식별하고, 적용 우선순위에 따라 판단
- **트레이드오프 발생 시**: 적용 우선순위를 따르되, 의도적 위반은 이유와 함께 기록
